할 일을 끝까지 적는다 Be clear and direct

모델은 맥락을 짐작하지 못한다. 결과물의 용도·독자·분량·형식을 문장 안에 다 적는다.

왜 듣나 "좋게 써줘"는 기준이 없어서 매번 다른 게 나온다. 기준을 적으면 같은 기준으로 다시 뽑을 수 있다.

이렇게 "고쳐줘" 대신 — Python 3.12, 외부 패키지 추가 없이, 기존 함수 시그니처 유지, 실패 케이스는 예외 대신 None 반환.

흔한 실수 길게 쓰는 것과 구체적으로 쓰는 것은 다르다. 형용사를 늘리지 말고 조건을 늘린다.

공식 문서 Anthropic 프롬프트 엔지니어링

역할을 먼저 준다 System prompt / role prompting

"너는 ○○다"를 시스템 프롬프트 자리에 두면 어휘와 판단 기준이 그 역할 쪽으로 기운다.

왜 듣나 같은 질문도 누구로서 답하느냐에 따라 고르는 근거가 달라진다.

이렇게 "이 코드를 3년 유지보수할 사람"으로 두면 짧은 코드보다 읽히는 코드를 낸다.

흔한 실수 역할을 지어낸 권위로 쓰면 안 된다. "너는 의사다"라고 해도 의학적 정확성이 생기지는 않는다.

공식 문서 Anthropic 시스템 프롬프트

설명 대신 예시를 준다 Multishot / few-shot prompting

원하는 결과물 2~5개를 그대로 보여준다. 말로 스타일을 설명하는 것보다 예시 한 줄이 정확하다.

왜 듣나 톤·길이·형식처럼 말로 옮기기 어려운 기준이 예시에는 그대로 들어 있다.

이렇게 팀 컨벤션에 맞는 함수 2개를 보여주면 네이밍·주석 밀도가 맞춰진다.

흔한 실수 예시가 전부 비슷하면 그 틀만 반복한다. 일부러 서로 다른 유형을 섞는다.

공식 문서 Anthropic 멀티샷 프롬프트

지시와 재료를 갈라놓는다 Use XML tags

시킬 일과 붙여넣은 자료를 태그로 구분한다. <자료>…</자료> <지시>…</지시> 처럼.

왜 듣나 길게 붙여넣으면 어디까지가 자료고 어디부터가 명령인지 섞인다. 자료 안의 문장을 명령으로 오해하는 일이 줄어든다.

이렇게 로그를 <로그>, 요구사항을 <요구사항>으로 나누면 로그 속 문자열을 지시로 실행하려 들지 않는다.

흔한 실수 태그 이름은 아무거나 좋지만 여닫는 짝은 맞아야 한다.

공식 문서 Anthropic XML 태그

결론 전에 근거를 쓰게 한다 Chain of thought

"바로 답하지 말고 먼저 따져볼 것을 적은 다음 결론"이라고 시킨다.

왜 듣나 중간 과정을 쓰게 하면 건너뛰던 단계가 드러나고, 틀렸을 때 어디서 틀렸는지 보인다.

이렇게 버그 원인을 물을 때 의심 지점을 먼저 나열시키면 첫 추측에 매몰되지 않는다.

흔한 실수 모든 일에 필요하지는 않다. 단순 변환·요약에 붙이면 길어지기만 한다.

논문 Wei et al. 2022, Chain-of-Thought Prompting

한 번에 하나씩 시킨다 Prompt chaining

큰 일을 단계로 쪼개 각 단계의 결과를 다음 단계 입력으로 넣는다.

왜 듣나 한 프롬프트에 여러 일을 담으면 뒤쪽 지시가 묻힌다. 단계를 나누면 중간에서 고칠 수 있다.

이렇게 ① 요구사항을 테스트 목록으로 → ② 테스트 통과 코드 → ③ 리팩터링.

흔한 실수 쪼갤수록 좋은 건 아니다. 사람이 중간 결과를 확인할 지점에서만 자른다.

공식 문서 Anthropic 프롬프트 연결

출력 형식을 못 박는다 Output formatting / prefill

표·JSON·번호 목록처럼 받을 형태를 지정하고, 답의 첫 부분을 대신 써준다.

왜 듣나 형식이 정해지면 그대로 붙여 쓸 수 있고, 여러 번 돌려도 모양이 같아 비교가 된다.

이렇게 JSON 스키마를 주고 그 형태로만 받으면 파싱 코드를 안 고쳐도 된다.

흔한 실수 형식을 바꾸면 결과의 질도 함께 달라질 수 있다. 비교할 때는 형식을 고정한다.

공식 문서 Anthropic 출력 미리 채우기

긴 자료는 위에, 질문은 맨 아래에 Long context tips

자료를 먼저 붙이고 질문을 마지막에 둔다. 자료가 길면 순서가 결과를 바꾼다.

왜 듣나 긴 입력에서는 가운데 있는 정보가 덜 쓰이는 경향이 보고돼 있다. 중요한 지시를 끝에 두면 묻히지 않는다.

이렇게 파일 여러 개를 붙인 뒤 맨 아래에 "이 함수를 호출하는 곳 전부".

흔한 실수 자료를 무작정 다 넣지 않는다. 필요 없는 부분을 지우는 게 순서 바꾸기보다 낫다.

논문 Liu et al. 2023, Lost in the Middle

답을 스스로 검사시킨다 Self-refine

초안을 받은 뒤 같은 모델에게 기준을 주고 "이 기준으로 흠을 찾아 고쳐라"고 시킨다.

왜 듣나 생성과 검토를 나누면 첫 답에서 놓친 조건이 걸러진다.

이렇게 "예외 처리 누락 / 경계값 / 기존 호출부 깨짐" 으로 코드를 검사.

흔한 실수 "더 좋게 고쳐줘"는 소용이 적다. 검사 기준을 항목으로 줘야 한다.

논문 Madaan et al. 2023, Self-Refine

여러 번 뽑아 겹치는 답을 고른다 Self-consistency

같은 질문을 여러 번 돌려 가장 자주 나온 결론을 택한다.

왜 듣나 한 번의 답은 흔들리지만 여러 번에서 겹치는 결론은 비교적 안정적이다.

이렇게 "이 로직의 시간 복잡도"처럼 답이 정해진 질문에 쓴다.

흔한 실수 답이 하나로 정해지는 문제에만 쓴다. 창작물은 많이 뽑아도 "정답"이 없다.

논문 Wang et al. 2022, Self-Consistency

하지 말 것 대신 할 것을 적는다 Positive instruction

"○○하지 마" 대신 "대신 ○○해"로 바꿔 쓴다.

왜 듣나 금지만 주면 그 자리를 무엇으로 채울지가 비어 있어 매번 다른 게 들어온다.

이렇게 "전역 변수 쓰지 마" → "상태는 인자로 넘기고 반환값으로 돌려줘".

흔한 실수 정말 금지해야 하는 것(개인정보·과장 표현)은 금지로 남기고 대안을 함께 준다.

공식 문서 Anthropic 프롬프트 엔지니어링 개요

근거를 인용하게 하고 확인한다 Grounding / quote first

붙여넣은 자료에서 근거 문장을 먼저 인용하게 한 뒤 답을 쓰게 한다.

왜 듣나 자료에 없는 말을 지어내는지 바로 드러난다. 인용이 비면 자료에 없는 것이다.

이렇게 문서 기반 답변에서 "해당 API 문서의 원문을 먼저 인용".

흔한 실수 인용이 있다고 참인 건 아니다. 인용 위치는 사람이 확인한다.
